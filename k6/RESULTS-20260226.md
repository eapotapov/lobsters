## Root Cause Analysis

### Story pages: query planner bug (confirmed)

SQLite broken is **56x slower** than MariaDB at production load (18.88s vs 339ms). The `story_threads` CTE query causes SQLite's planner to pick the wrong index, scanning ~186k rows per request. The two-line fix resolves it completely — SQLite fixed (242ms) outperforms MariaDB (339ms).

At production load, SQLite broken **drops 86% of incoming requests** and serves only 2.5 req/s. The site is effectively unusable.

### Homepage: also a query planner problem

Investigation confirmed the homepage slowdown is **not** a SQLite concurrency/single-writer issue. It is a second query planner problem.

**Evidence:**

1. **EXPLAIN query plans differ.** The homepage query (`SELECT * FROM stories WHERE ... ORDER BY hotness LIMIT 26`) uses different indexes:
   - MariaDB: `USING INDEX hotness_idx` — walks the B-tree in order, stops after 26 rows
   - SQLite: `USING INDEX index_stories_on_merged_story_id` + `TEMP B-TREE FOR ORDER BY` — finds all 119,801 rows where `merged_story_id IS NULL`, sorts them all, takes 26

2. **Raw SQL confirms the gap without concurrency.** Single-connection timing:
   - MariaDB: ~5–8ms (warm)
   - SQLite: ~55–62ms (warm)
   - 10x difference from the query plan alone

3. **1 VU test still shows the gap.** With concurrency eliminated (1 virtual user):
   - MariaDB: 112ms avg
   - SQLite broken: 156ms avg (1.4x)
   - SQLite fixed: 193ms avg (1.7x)
   - The gap exists even without concurrent load, proving it's not a locking issue

4. **The `hotness_idx` exists in SQLite but is not used.** SQLite's planner chooses `merged_story_id` because the `OR` in `(is_deleted = 0 OR user_id = 0)` makes it estimate that index is more selective. It's not — 119,801 of 120,000 rows have `merged_story_id IS NULL`.

### Summary

Both the story page and homepage slowdowns are **SQLite query planner issues** — the planner picks suboptimal indexes for queries with compound WHERE clauses. The story page bug is catastrophic (56x slower); the homepage bug is moderate (~2x slower) but causes the site to drop 30% of requests at production load.

## Failure Rate

All tests: **0% HTTP failure rate** across all versions and endpoints. Dropped iterations are requests k6 could not send because the server was too slow to accept them at the target rate.
