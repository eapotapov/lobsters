# k6 Performance Test Results — 2026-02-26

## Test Setup

- **Load generator:** [lobsters-k6](https://lobsters-k6.eapotapov.dev/reports/) (68.183.105.136, s-4vcpu-8gb, nyc1)
- **Tool:** k6 v1.6.1
- **Parameters:** 10 virtual users, 5 minutes per test, 500ms sleep between requests
- **Test scripts:** [`homepage-single.js`](../k6/tests/homepage-single.js), [`story-page-single.js`](../k6/tests/story-page-single.js)

### Targets

| Version | URL | Description |
|---|---|---|
| MariaDB | https://lobsters-mariadb.eapotapov.dev | Current production codebase (commit `9b736939`) |
| SQLite broken | https://lobsters-1871.eapotapov.dev | PR #1871 as-deployed (commit `74544e96`) |
| SQLite fixed | https://lobsters-1927.eapotapov.dev | Fork with `story_threads` query fix (commit `936ccb69`) |

All three databases contain identical data: 5,000 users, 120,000 stories, 675,000 comments, 4,000,000 votes (~7.2M rows).

## Analysis

**Story pages confirm the root cause.** The SQLite broken version is **26x slower** than MariaDB on story pages (3,640ms vs 141ms avg). This is the `story_threads` CTE query where SQLite's query planner picks the wrong index, causing a full table scan of ~186k rows per request.

**The fix works.** SQLite fixed (127ms avg) is actually **slightly faster** than MariaDB (141ms avg) on story pages, confirming that the two-line query fix completely resolves the bottleneck.

**Homepage is a different story.** Both SQLite versions show ~2x overhead on the homepage regardless of the fix. This is expected — the homepage does not use the `story_threads` query. The overhead comes from SQLite's single-writer concurrency model under load.

**Throughput impact:**
- Story pages: broken SQLite serves **6.5x fewer requests** (729 vs 4,678) in the same time window
- Homepage: SQLite serves ~20–26% fewer requests than MariaDB

## Failure Rate

All tests: **0% failure rate** across all versions and endpoints.
