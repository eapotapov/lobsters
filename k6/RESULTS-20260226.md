## Production Load Tests (20 req/s)

Sends a constant 20 req/s for 1 minute to measure response times and dropped requests under production-realistic load. Lobsters typically sees 15–25 req/s.

**Scripts:** [`homepage-production.js`](tests/homepage-production.js), [`story-page-production.js`](tests/story-page-production.js) — constant-arrival-rate executor, sends exactly 20 req/s regardless of server speed. Requests that can't be sent in time are counted as dropped.

```bash
k6 run --out web-dashboard=export=/srv/k6/reports/<name>.html \
  -e TARGET_URL=https://<host> -e DURATION=1m tests/homepage-production.js

k6 run --out web-dashboard=export=/srv/k6/reports/<name>.html \
  -e TARGET_URL=https://<host> -e DURATION=1m tests/story-page-production.js
```

## Stress Tests (10 / 20 / 40 VUs, max throughput)

Concurrent virtual users request pages as fast as possible for 1 minute at increasing VU levels, to map the performance curve and find maximum throughput each version can sustain.

**Scripts:** [`homepage-single.js`](tests/homepage-single.js), [`story-page-single.js`](tests/story-page-single.js) — constant-vus executor, VUs loop as fast as possible. No target rate, so no dropped requests — total requests reflect maximum throughput.

**Runner:** [`run-stress-matrix.sh`](tests/run-stress-matrix.sh) — runs all combinations of VU levels × versions × endpoints.

```bash
bash tests/run-stress-matrix.sh --duration 1m
```

## Root Cause Analysis

### Story pages: query planner bug (confirmed)

SQLite broken is **143x slower** than MariaDB at production load (17.22s vs 120ms). The [`story_threads`](https://github.com/lobsters/lobsters/blob/74544e96/app/models/comment.rb#L186-L216) CTE query causes SQLite's planner to pick the wrong index, scanning ~186k rows per request. See [INVESTIGATION.md](../INVESTIGATION.md) for the full root cause analysis.

The [two-line fix](https://github.com/eapotapov/lobsters-sqlite-fix/commit/936ccb69) resolves it completely — SQLite fixed (124ms) matches MariaDB (120ms) at production load with zero dropped requests.

At production load, SQLite broken **drops 84% of incoming requests** and serves only 2.5 req/s. The site is effectively unusable.

The stress tests confirm this is a per-request query planner issue, not a concurrency problem: SQLite broken throughput stays flat at ~2.3 req/s regardless of VU count (10 → 20 → 40), while latency scales linearly (4.3s → 8.0s → 15.4s).

### Homepage: also a query planner problem

Investigation confirmed the homepage slowdown is **not** a SQLite concurrency/single-writer issue. It is a second query planner problem, traced to a specific scope in the codebase.

#### Code path

The homepage controller calls [`Story.hottest`](https://github.com/lobsters/lobsters/blob/74544e96/app/models/story.rb#L83-L88):

```ruby
# app/models/story.rb:83-88
scope :hottest, ->(user = nil, exclude_tags = nil) {
  base(user).not_hidden_by(user)
    .filter_tags(exclude_tags || [])
    .positive_ranked
    .order(:hotness)
}
```

The [`base`](https://github.com/lobsters/lobsters/blob/74544e96/app/models/story.rb#L61-L65) scope chains [`not_deleted`](https://github.com/lobsters/lobsters/blob/74544e96/app/models/story.rb#L76-L78) and [`unmerged`](https://github.com/lobsters/lobsters/blob/74544e96/app/models/story.rb#L79):

```ruby
# app/models/story.rb:76-78
scope :not_deleted, ->(user) {
  user.try(:is_moderator?) ? all : where(is_deleted: false).or(where(user_id: user.try(:id).to_i))
}
```

For anonymous visitors (`user = nil`), this generates:

```sql
SELECT "stories".* FROM "stories"
WHERE ("stories"."is_deleted" = 0 OR "stories"."user_id" = 0)
  AND "stories"."merged_story_id" IS NULL
  AND (score >= 0)
ORDER BY "stories"."hotness" ASC
LIMIT 26
```

The `OR user_id = 0` clause matches zero rows (no user has id 0) but prevents SQLite from using `hotness_idx`.

#### Query plan comparison

```sql
-- MariaDB
EXPLAIN SELECT * FROM stories
WHERE (is_deleted = 0 OR user_id = 0) AND merged_story_id IS NULL AND score >= 0
ORDER BY hotness ASC LIMIT 26;

-- SQLite
EXPLAIN QUERY PLAN SELECT * FROM stories
WHERE (is_deleted = 0 OR user_id = 0) AND merged_story_id IS NULL AND score >= 0
ORDER BY hotness ASC LIMIT 26;
```

**MariaDB** — uses [`hotness_idx`](https://github.com/lobsters/lobsters/blob/74544e96/db/schema.rb#L399) directly:
```
USING INDEX hotness_idx  →  walks B-tree in hotness order, stops after 26 matches
```

**SQLite** — picks the wrong index:
```
SEARCH stories USING INDEX index_stories_on_merged_story_id (merged_story_id=?)
USE TEMP B-TREE FOR ORDER BY
```
Finds all 119,801 rows where `merged_story_id IS NULL` (99.8% of 120k stories), sorts them all by hotness in memory, then returns 26.

Both indexes exist in the SQLite [schema](https://github.com/lobsters/lobsters/blob/74544e96/db/schema.rb#L399-L403):
```ruby
# db/schema.rb:399-403
t.index ["hotness"], name: "hotness_idx"
t.index ["merged_story_id"], name: "index_stories_on_merged_story_id"
```

#### Evidence

1. **EXPLAIN plans differ** (see above). The `OR` in `not_deleted` makes SQLite's planner estimate that `merged_story_id` is more selective than walking `hotness_idx`. It's not — 119,801 of 120,000 rows have `merged_story_id IS NULL`.

2. **Raw SQL confirms the gap without concurrency.** Single-connection timing:
   - MariaDB: ~5–8ms (warm)
   - SQLite: ~55–62ms (warm)
   - 10x difference from the query plan alone

3. **Multi-VU stress tests confirm the gap is from query speed, not locking.** Both SQLite versions plateau at ~12–13 req/s across all VU levels (10 / 20 / 40), while MariaDB sustains ~18–20 req/s. If this were a concurrency/locking issue, SQLite would degrade disproportionately as VUs increase. Instead, throughput stays flat while latency scales linearly — the signature of a per-request bottleneck.

### Summary

Both the story page and homepage slowdowns are **SQLite query planner issues** — the planner picks suboptimal indexes for queries with compound WHERE clauses. The story page bug is catastrophic (143x slower); the homepage bug is moderate (~1.5x slower throughput) but causes the site to drop ~30% of requests at production load.

## Failure Rate

All tests: **0% HTTP failure rate** across all versions and endpoints. Dropped iterations are requests k6 could not send because the server was too slow to accept them at the target rate.
